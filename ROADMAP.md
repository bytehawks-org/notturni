# Specifications and status

This document is the practical reference for understanding **what the project plans**,
**what has already been implemented** and **what remains to be done**. It also serves as a workplan:
the rows marked 🟡 and ⚪ are, in practice, the open tasks.

The product vision (goals, tone, reference examples, initial architectural constraints) is described in
[docs/ABSTRACT.md](docs/ABSTRACT.md). This file tracks, spec by spec, what is implemented,
partial or still to do, checked against the actual state of the code.

The backend is written in Rust (Cargo workspace): code references in the notes point to crates
and modules (`crates/…`, `modules/…`); the map between the v1 Python files and their current location is in
[docs/BACKEND.md](docs/BACKEND.md#from-v1-where-things-went). Notes that describe fixes made to the Python
implementation refer to v1 and are kept as history.

Status legend:

- ✅ **Implemented** — present in the code and covered by tests and/or manual verification.
- 🟡 **Partial** — present but with known limitations, or infrastructure ready and not yet connected
  to application logic.
- ⚪ **To do** — not started yet.

A headless browser on `/login?mfa_challenge=...&mfa_method=totp` correctly shows the existing 6-digit OTP form. |
| Account linking based on email, with 2FA gate | ✅ | |
| API tokens (`api_tokens`, prefix `noct_`, sha256 hash) | ✅ | Full "core" (engine, machine-to-machine) and "user" tokens. `POST/GET/DELETE /api/v1/tokens` accept both an existing opaque ApiToken (core bootstrap and rotation) and a JWT session (for the *first* user token, from the dashboard, which is the core authentication). | GDPR: MFA/2FA as account security hardening | ✅ | See above. No GDPR-specific functionality beyond this (see the dedicated row in [1](#1-product-and-domain-rules)). |
| Session in `localStorage` | ✅ | Replaced. The refresh token now lives only in an `httpOnly` + `Secure` + `SameSite` cookie set by the backend (`crates/noct-auth`), never in the JSON body or in `localStorage`. The access token (15 min) stays in the response body, but the frontend keeps it only in memory (`frontend/src/lib/auth-context.tsx`). A full reload requires a silent refresh at startup, which is already handled. CSRF protection (double-submit `noct_csrf_token` plus the `X-CSRF-Token` header) applies only to the endpoints authenticated by cookie (`/auth/refresh`, `/auth/logout`).
