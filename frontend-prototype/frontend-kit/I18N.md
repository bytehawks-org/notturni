# Interface i18n (next-intl)

Two layers, kept separate:
- **Content** (posts, pages, blog languages): already modelled by the backend (locale + slug per translation). Unchanged.
- **Interface** (labels, buttons, messages): `next-intl`, messages in `messages/{locale}.json`, supported locales in `i18n/config.ts` (`en`, `it` today — add a JSON file + the code to `LOCALES` for more).

## Default language
- Install time: `NOCT_DEFAULT_LOCALE=en|it` (backend exposes it as `default_locale` in `GET /api/v1/config`).
- Runtime: Super admin → Platform settings → *Default interface language* (`PATCH /api/v1/admin/config { default_locale }`), audited.
- Per user: profile → *Interface language* (`users.ui_locale`, nullable = follow platform default). Signed-out visitors: cookie from the header picker, else platform default, else Accept-Language.

Resolution order is implemented in `i18n/request.ts`; `i18n/actions.ts` sets the cookie; `components/shell/UiLanguagePicker.tsx` is the control.

## Install
`npm i next-intl`, copy `i18n/`, `messages/`, apply `next.config.snippet.ts` and the layout note in `layout-fonts.tsx`. Server components use `getTranslations()`, client components `useTranslations()` — already wired in every kit component. Plurals use ICU (`{count, plural, one {…} other {…}}`).

## Backend additions
- `platform_config.default_locale` (enum en|it, default from `NOCT_DEFAULT_LOCALE`), returned by `/config`, editable by Super admin.
- `users.ui_locale` nullable enum; returned in `/users/me`; the frontend mirrors it into the cookie on login.
- Emails (OTP, invitations) should use the recipient's `ui_locale` ?? platform default.
